# A Deployment keeps its data in its own folder, and the Operator gets Hermes Agent's Dashboard on loopback

> Amended by [ADR 0009](0009-every-way-to-run-is-a-container.md): `home/` and `workspace/` may be moved with `HERMES_HOME_DIR`/`HERMES_WORKSPACE_DIR`, every container runs as 10000:10000, containers have fixed names, and `/opt/data` is kept in named volumes.

Each Deployment now lives in one folder on the server, `deploy/deployments/<team>/`, created by `deploy/new-deployment` and run with `deploy/cowork`. Its `.env`, `home/` (everything the Deployment keeps), `workspace/` and `certs/` are bind-mounted from that folder instead of being kept in named Docker volumes. Only the agent's installed source stays a named volume (`gfit-<team>_hermes-agent-src`), because the agent image fills it and it is thrown away on every agent upgrade. We chose this so the Operator can see, back up and restore a whole Deployment as one folder with ordinary tools (`tar`, `rsync`, the server's own backup), without `docker run` recipes for each volume, and because `new-deployment` can give each Deployment its ports and secrets at the moment it creates the folder.

The kit also runs Hermes Agent's own **Dashboard** (`hermes-dashboard`, the agent image's `dashboard` command) next to the gateway. It is for the Operator only: it listens on `127.0.0.1:<DASHBOARD_PORT>` on the server, is never put behind the reverse proxy, and is reached over an SSH tunnel with its own login from `.env`.

This keeps ADR 0006. GFIT-CoWork still has one role, the User, and no web route for anyone else: the Dashboard is not part of GFIT-CoWork, has no login from AD, and is reachable only by someone who already has shell access to the server, which is the Operator ADR 0006 describes ("Hermes Agent's own tools"). What ADR 0006 deleted was the Upstream dashboard inside the web app, open to an Admin through the same login as Users; that stays deleted.

## Considered Options

- **Keep named volumes.** Docker owns the files, so UID/GID never needs setting up on the host. Rejected: backup and restore need a `docker run` recipe per volume, the data is hidden under Docker's own directory, and moving a Deployment to another server means exporting volumes one by one.
- **Bind mounts, but keep copying the kit into a folder per Team by hand.** Rejected: the Operator had to pick ports and generate secrets by hand for every Team, and nothing stopped two Teams from getting the same port.
- **No Dashboard.** Rejected: the Operator already has every power the Dashboard gives (it does what `hermes ...` does in a shell), and the Dashboard is a faster way to see the gateway's state, sessions and logs during a pilot.
- **The Dashboard behind the reverse proxy.** Rejected: it would put an all-powerful page on the company network, guarded only by one shared password.

## Consequences

- **Persistence.** `deploy/cowork <team> down` (even `down -v`) never deletes `home/` or `workspace/`; only the folder holds them. Deleting the folder deletes the Deployment. `-v` only removes the agent source volume, which the next `up` fills again.
- **File permissions.** `new-deployment` writes the Operator's `id -u` / `id -g` to `UID` / `GID` (1000:1000 when run as root, and gives `home/` and `workspace/` to that user), and every container runs as that UID/GID. `.env` is created mode 600 and `deploy/deployments/` mode 700. `home/` holds every Profile's keys: anyone who can read it on the host can read them.
- **Backup and restore.** Back up by stopping the Deployment and copying its folder (`deploy/README.md`); leave out the empty `home/hermes-agent/` mount point. Restore by putting the folder back on a server with the same checkout and running `deploy/cowork <team> up -d`. A backup holds `.env` and every Profile's keys, so it must be kept as safely as the server.
- **Migration.** A Deployment made before this kit kept its data in `gfit-<team>_hermes-home` and `gfit-<team>_admin-workspace`. `deploy/README.md` shows how to copy them into a new folder of the same Team name; keep the old volumes until the Team has checked their Profiles.
- **SQLite on Docker Desktop.** On macOS and Windows Docker Desktop, a bind mount crosses a VM boundary, so Hermes Agent turns off SQLite WAL for databases in `home/` (it logs a warning) and uses `journal_mode=DELETE`. This is safe but slower under load. On the Linux server a Deployment runs on, the bind mount is a native filesystem and WAL stays on. Do not measure a pilot's capacity on Docker Desktop.
- **Ports.** `new-deployment <team> <N>` gives GFIT-CoWork `2NN87` and the Dashboard `2NN19` (N=0: 8787 and 9119) and refuses an N or a Team name already in use. It does not check whether another program already listens on the port; `up` fails with Docker's error if so. Hermes Agent's gateway (8642) and A2A are never published (A2A waits for the Reception, ADR 0003).
- **The Dashboard's key.** Every service that runs the agent image must get the Deployment's `API_SERVER_KEY`. Without it, the image's start-up writes a random key into the shared `home/.env`, which the gateway then loads over its own, and GFIT-CoWork is refused by the gateway. A test keeps every agent-image service on the Deployment's key.
- **The gateway key in `home/.env`.** Once a Deployment has two or more Profiles, Hermes Agent v0.21.6 runs its gateway multiplexed and reads `API_SERVER_KEY` only from the default Profile's `.env` (`home/.env`), not from the container's environment; without it there the gateway's API never starts after a restart and GFIT-CoWork cannot reach it. So `deploy/cowork` copies the key from the Deployment's `.env` (the only source of it) into `home/.env` before every `up`, `start`, `restart`, `create` and `run`. It replaces any other `API_SERVER_KEY` line, keeps every other line, writes the file atomically with mode 600, does nothing when the key already matches, never prints the key, and starts nothing if it cannot write the file or if `home/` or `home/.env` is a symlink. It never replaces the file while any of the Deployment's containers run (or when it cannot tell), because Hermes Agent writes the same file and a replace could lose that write; a changed key needs `down`, then `up -d`. This puts the key where every User's agent can read it; that is accepted, because those agents already run as the same OS user as the gateway in the same container (ADR 0002) and the gateway is not published outside the Deployment.
- **What the Dashboard can do.** It can create, rename and delete Profiles, change their model and config, open a terminal and control the gateway, like `hermes ...` in a shell. It does not know the Profile roster. So the Operator keeps using GFIT-CoWork's command line for the Profile lifecycle (create, disable, enable, delete), because only that disables a Profile before deleting it and keeps the roster right. The Dashboard is for looking at the agent and changing its own settings.
- **Security.** The Dashboard's login is a shared username and password in `.env`, rate-limited by the Dashboard itself; it is not a person's AD account, and its use is not tied to anyone. Give it only to Operators. Its `/api/status` answers without a login and lists the Profile names (employee IDs), the version and the gateway state; on loopback only the server's own users can reach it, which is why the Dashboard must never be published beyond `127.0.0.1`. The Dashboard does not get the Deployment's `.env` (no AD values, no provider key), only its own login and the gateway key.
- `deploy/docker-compose.yml` is run only through `deploy/cowork`, which sets the project directory to the Deployment's folder and refuses to start one whose AD values, provider key or AD CA certificate are missing. ADR 0005 still holds: `deploy/` is the one way to run a Deployment, and there is no Compose file at the root.
